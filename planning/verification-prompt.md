## 検証対象の主張

### 外部事実（一次資料で確認）
- **F1**: 日本の厚生労働省「医療情報システムの安全管理に関するガイドライン 第6.0版」が存在し、医療情報システムの公的な安全管理基準である。→ **現在の最新版が6.0かどうか（その後の改定の有無）も必ず確認**。
- **F2**: FHIR (Fast Healthcare Interoperability Resources) は HL7 (Health Level Seven) が策定した医療情報交換標準で、Resources というモジュール単位、API重視設計、JSON/XML/HTTP/OAuth と整合する。
- **F3**: HSM (Hardware Security Module) は NIST が「暗号鍵を保護・管理し、暗号処理を提供する物理デバイス」と定義し、耐タンパ性・侵入耐性を備える。

### 設計結論（技術的妥当性と 2024–2026 の最新動向を評価）
- **C1**: ブロックチェーンは医療記録本体の保存先ではなく、同意・アクセス権・監査証跡の記録層として使うべき。
- **C2**: 実データは暗号化してオフチェーン保存し、ブロックチェーンには参照(CID)と権限のみを載せる。
- **C3**: 日本では患者単独の秘密鍵方式より、患者・病院のハイブリッド鍵管理が現実的。
- **C4**: 単純な秘密鍵共有でなく、MPC（マルチパーティ計算）・閾値署名・プロキシ再暗号化で分散管理する。
- **C5**: 病院側の鍵管理には HSM が有力。
- **C6**: 既存電子カルテへの導入は全面置換でなく FHIR ブリッジ型が現実的。
- **C7**: 「台帳の分散複製」と「実データ（IPFS等）の冗長化」は別レイヤーとして分けて設計すべき。
- **C8**: 他院への診療情報提供では、提供先を常に IPFS クラスターに参加させる必要はなく、ゲートウェイ経由で暗号化データを取得し別チャネルで復号権限を付与する構成が実務的。
- **C9**: 真の価値は保存技術そのものでなく、標準化された高品質な医療データの活用にある。
- **C10**: LLM 活用は診断でなく「医療機関管理下の患者説明支援」に寄せるのが安全・現実的。Confidential Computing 的構成の可能性も。
- **C11**: 研究利用は患者同意を前提に、診療記録＋LLM対話ログを仮名化して段階的に収集する構想。
