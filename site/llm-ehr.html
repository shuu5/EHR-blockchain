LLM × EHR 統合 考察

ブロックチェーン管理EHRを LLM に渡す
— 同意 → 復号 → コンテキスト取得の E2E 統合

検証ビューア（C1–C11）の先にある2本の探索的考察を可視化したものです。患者の同意に基づき LLM が暗号化カルテを復号してコンテキストとして取得するエンドツーエンド統合の具体設計、最重要のセキュリティ懸念、そして「ベクトルRAGより構造化ナビゲーション優位」という実証的修正を整理します。さらに後半の「現実チェック」では、院内LLMの脅威モデル・BCの必要十分性・海外の統合事例・断片化のナッシュ均衡から、この構想がどんな前提で成立するかを問い直します。各主張には 信頼度ラベル（確証 / 論理導出 / 状況推測 / 未確認）を付与しています。

概要・最重要発見

本構想の核心は「患者がスマートコントラクトで同意 → LLM がオフチェーンの暗号化カルテを復号 → コンテキストとして取得」という一連のループです。2本の調査（research:controller-search・重視期間2024–2026、いずれも critic 判定 PASS）の結論を、まず1つの最重要メッセージと5つの発見にまとめます。

本プロジェクトの貢献余地

E2E ループ全体を一気通貫で実装した一次文献は、2026-05 時点で存在しない＝研究フロンティア。

同意ゲート（EIP-712）・復号権付与（MA-ABE／閾値PRE）・鍵の安全到達（attestation-gated key release）・TEE 推論・オンチェーン監査（AuditEvent＋Merkle）は、構成要素の一つ一つが一次文献・公式 docs で実コード／API 仕様まで具体化できる成熟段階に達しています。しかし、それらを「同意 → 復号 → LLM コンテキスト」として結ぶ統合プロトコルは未だ文献に不在（researcher-1/2/3 が独立に同じ空白を報告）。この統合の設計こそが本プロジェクトの貢献余地です。

コンテキスト注入方式の比較 ★ 最重要論点

患者1人分の FHIR レコードは平均約300万トークンに達し、全量注入は不可能です。前回調査は「ベクトルRAG が支配的設計」と結論しましたが、本調査はこれを一次ソースで実証的に修正しました — 医療／FHIR 文脈では構造化ナビゲーション＋語彙的検索が優位です。

E2E 統合 — 9ステップのシーケンスと信頼境界

焦点1〜4を統合した E2E フロー。各ステップは異なる信頼境界をまたぎます。色は 灰=クライアント・青=ブロックチェーン/監査・紫=鍵管理・TEE。最重要の信頼境界は TEE（ハードウェア隔離）で、ステップ⑤〜⑧を囲んで強調しています。各ノードにカーソル（またはフォーカス）を合わせると主体・保証・残存リスクが出ます。

図A: 「同意 → 復号 → コンテキスト取得 → 監査」の流れ

患者の EIP-712 署名から始まり、スマートコントラクトの同意ゲート、復号権付与、アテステーション連動の鍵払い出しを経て、TEE 内で復号・取得・推論し、最後に本文を含まない監査証跡をオンチェーンに残します。

主要セキュリティ懸念6項目と緩和策

本テーマ固有の最重要懸念は (a) 間接プロンプトインジェクション — ブロックチェーンで正当に復号・取得したカルテ本文そのものが攻撃ベクターになります。各懸念に「第一防御」と「補完防御」を対応づけました。

図B: TEE でも防げない残存リスク（サイドチャネル・2025–2026 実証）

「TEE ＝ 万能」ではありません。ハードウェア隔離の内側でも、処理の副次情報から秘密が漏れる実証が複数あります。各ボックスにカーソルで詳細。

4層防御アーキテクチャ（Defense-in-Depth）

取得データを「信頼境界の外側」として扱う前提で、入力前（Layer 0）→ RAG（Layer 1）→ 推論時（Layer 2）→ 出力・監査（Layer 3）の4層に、認証・認可と推論環境という2つの横断的防御を加えます。各層は前章のセキュリティ懸念に対応します。

図C: Layer 0–3 ＋ 横断防御と、対応する懸念

LLM を中心に、入力から出力までを4層が包みます。上下の帯（認証・認可／推論環境）は全層に横断的にかかります。中央の橙の帯は本テーマの核心 —「取得カルテ本文＝信頼境界の外側」。各要素にカーソルで補足。

参照フレームワーク: NIST AI RMF ／ OWASP LLM Top 10（2025）／ ISO/IEC 42001 ／ 仮名化ワークフロー（arXiv 2505.08728）。【確証〜論理導出】

ブロックチェーン統合 — オン/オフチェーンの分担

ブロックチェーンの役割は「コンテキストの供給」ではなく「同意ゲート＋アクセス制御＋改ざん耐性ある監査証跡」（既存 C1 と一致）。実データと推論はオフチェーン／TEE で扱います。色は検証ビューアと共通で 青＝オンチェーン・緑＝オフチェーン。

図D: 記録層（オンチェーン）と実体層（オフチェーン）の分担

オンチェーンには本文を一切置かず、ハッシュ・参照子・許可イベント・監査のみ。実データ・LLM 推論・重い暗号演算はオフチェーン／TEE。両者は鍵管理（C3 二者分散）で橋渡しされます。各要素にカーソルで補足。

AuditEvent スキーマ（本文・氏名・生データは一切載せない）

GDPR 第17条（忘れられる権利）との両立: 本文をオフチェーン暗号化＋ハッシュのみオンチェーンとし、消去は「オフチェーンデータ削除＋復号鍵の安全消去（key erasure）」でオンチェーンハッシュを事実上アクセス不能化。患者IDは H(patient_id‖epoch_salt) とし、消去時にソルトをローテーション／削除（EDPB Guidelines 02/2025 と整合）。【論理導出】

現実チェック — Reality Check

この構想は、どんな前提で成立するか

ここまでは「技術的にどう実装するか」を扱いました。ここからは視点を引いて、2本の批判的再検証レポート（院内LLMの脅威モデル・BC必要性・患者アクセス・統合現実性＝85ソース／海外の統合事例＝94ソース、いずれも critic 判定 PASS）に基づき、「そもそもこの構想はどんな前提が成立したときに活きるのか」を4つの問いで現実チェックします。結論を先取りすると ― ブロックチェーンは技術的必然ではなく、trustless な多機関・患者主権の法的強制という前提に賭けた条件付き設計であり、現実解はむしろ連携（federation）＋標準化です。

院内LLMで懸念は消えるか BC は必要十分か 単一統合は起こるか なぜ断片化は続くのか

脅威の重心移動 — 院内LLMという前提 現実チェック ①

「院内（オンプレ・シングルテナント）で動かせば、今回のセキュリティ懸念の多くは当たらないのでは？」というユーザーの直感を検証しました。結論は概ね支持 ― 外部クラウドAPI特有の脅威は構造的に消滅する一方、LLM と内部の人・データに起因する脅威は残り、脅威の重心が「外部送信」から「取得内容・運用」へ移動します。

✓ 確証 院内化で「消える」脅威

いずれも「外部の他者とインフラを共有する」ことに起因 → シングルテナント院内完結で前提そのものが消滅する。

  • 消滅外部API送信によるユーザー推論攻撃（出力プロービングで希少コホート適応を判定）
  • 消滅マルチテナントのサイドチャネル（中間アクティベーション反転）
  • 消滅KV-Cacheタイミング攻撃（クロステナントのプロンプトプレフィックス漏洩）
  • 消滅クラウド運営者・データセンター事業者による入力／出力／中間表現の閲覧
  • 消滅WAN通信のタイミング・パケットサイズからのPHI密度推定

✓ 確証 院内化でも「残る」脅威

「LLM という仕組み自体」と「内部の人・データ」に起因し、院内化では消えない。重心が内容・運用へ移動する。

  • 残存 ★間接プロンプトインジェクション（最重要） ― 臨床LLM実験で攻撃成功率 94.4%（4ターン）・禁忌薬推薦 91.7%。最新モデルでも脆弱。
  • 残存内部者脅威（臨床スタッフ／データエンジニア／システム管理者の3類型）
  • 残存ハルシネーション（本番化でフィードバック率が 5.8%→1.3% に低下しモニタリング困難化）
  • 残存ログ漏洩（デバッグ／ETLログにPHI混入）・独自ファインチューニング時の訓練データ記憶化
TEE／リモートアテステーションの要否: 完全院内オンプレ＋信頼できる職員＋物理セキュリティ＋単一テナントなら、TEE・リモートアテステーションは必須でない（検証相手が存在しない）。TEE が要るのは ①インフラ運営者を信頼できない（外部委託DC）②モデルIP保護 ③複数病院フェデレーション ― の3ケース。ただし大規模モデル（32B+）で TEE オーバーヘッドは1%未満（H100/H200 でネイティブ性能 95–99% 維持）＝「不要だが、入れても実害は小さい」水準。【論理導出】

ブロックチェーンは必要十分か 現実チェック ②

「BC による患者同意・患者アクセスは本当に必要か。中央集権ソブリンクラウドや標準APIで代替できないか」。結論 ― 大半のケースで代替可能。現実の旗艦事例は BC を使わない中央集権で、患者アクセスは OAuth2/OIDC＋SMART on FHIR で技術的に十分。BC が必要十分なのは trustless な多機関の限定シナリオに限られます。

本調査の最重要発見

医療ソブリンクラウドの旗艦事例（富士通×IBM）は、ブロックチェーンを一切使わない中央集権モデルだった。

2026-05-15 に正式発表された富士通×日本IBM の医療ソブリンクラウドは、Oracle Alloy ベースの中央集権クラウドを共通基盤に電子カルテを稼働させる構成です。ブロックチェーン／分散台帳／スマートコントラクトへの言及は、調査した全ての一次・二次ソースで皆無でした。同意・アクセス制御はソブリンクラウド＋（推定）SMART on FHIR 系 IAM が担います。「医療ソブリンクラウドは BC で患者同意を実装する」という想定は、現実の旗艦事例では成立していません。✓ 確証

出典: 富士通・日本IBM 協業具体化（公式PR 2026/05/15） ／ Fujitsu to use Oracle Alloy（DCD）

患者アクセス — OAuth2/OIDC＋SMART on FHIR で十分（BC は上位補完レイヤー）

米 CMS-9115-F（2021）／CMS-0057-F（2024）が Patient Access API（FHIR＋OAuth2＋SMART）を義務化（初回メトリクス報告 2026-03-31）。日本も JP-CLINS＋マイナポータルAPI（電子カルテ情報共有サービス、2025/02 モデル事業）で実現し、いずれもブロックチェーンを使いません。多くの論文が「BC 同意 ≠ OAuth2 の代替、BC は上位補完レイヤー」と位置づけます。

観点OAuth2/OIDC＋SMART on FHIRBC 同意

BC が技術的に勝るのは「分散・不変な監査」と「細粒度の同意」のみ。患者アクセスの必須要件とする根拠はない。出典: CMS Patient Access API FAQ ／ SMART App Launch v2.2.0（HL7） ／ 電子カルテ情報共有サービス（厚労省）

単一統合は起こるか — 海外事例とソブリンウォッシング 現実チェック ③

「日本で医療カルテを単一ソブリンクラウドに統合するのは現実的か」を 94 ソースの海外事例で検証しました。結論 ― 単一中央DB統合は構造的に失敗しやすく、成功は連携型か小国／単一州の強制統一に限られます。「ソブリンクラウド」自体も主権の形骸化（ソブリンウォッシング）に陥りやすいことが分かりました。

図E: 集中型（単一中央DB）vs 連携型（federation）

左は全機関を単一中央DBに接続する集中型（英NPfIT の Spine 等）＝単一障害点・過大な野心で失敗しやすい。右は各機関がデータを保持し交換層で相互運用する連携型（X-Road 等）＝中央DBを作らず成功している。各要素にカーソル（またはフォーカス）で補足。

なぜ断片化は続くのか — ナッシュ均衡とメタ結論 現実チェック ④

断片化は「怠慢」ではなく「合理的な安定均衡」です。ベンダー・病院・政府の三者すべてにとって現状維持が支配戦略であり、誰も一方的に動く動機を持ちません。最後に、4つの現実チェックを統合したメタ結論を示します。

図F: 断片化を維持する三者のナッシュ均衡

EHRベンダー・病院・政府の三者は、それぞれにとって「共有しない／現状維持／任意参加」が支配戦略になります。結果として誰も一方的に逸脱せず、断片化が安定均衡として持続します。各ノードにカーソル（またはフォーカス）で補足。

≈ 状況推測 ナッシュ均衡としての定式化は理論的説明であり、一次根拠は技術ブログ／Medium 中心（査読経済学での直接定式化は限定的）。情報ブロッキング・Epic 寡占などの個別事実は査読・公式統計で確証。出典: Vendor Lock-In Economics: Nash Equilibrium ／ Information blocking remains prevalent（PMC） ／ Political Economy of Digital Health（JMIR/PMC）

メタ結論

原典のブロックチェーンは「技術的必然」ではなく「条件付き設計」

4つの現実チェックを統合すると ― ① 院内LLMは外部API系の懸念を消すが、間接プロンプトインジェクション等は残す。② BC同意は旗艦事例で採用されず、中央集権ソブリンクラウド＋SMART on FHIR が代替する。③ 患者アクセスは標準APIで十分。④ 単一統合は海外で繰り返し失敗し、断片化は安定均衡として続く。皮肉にも、この「断片化・多機関・相互不信」の状況こそ BC が理論上もっとも正当化されるシナリオですが、現実の連携手段は FHIR／全国医療情報プラットフォームが先行し、BC は補完層に留まります。

したがって原典の BC は、trustless な多機関・患者主権の法的強制という前提が成立したら活きる「条件付き設計」と理解するのが最も整合的です（既存 C1「BC＝同意・権限・監査の記録層」と一致）。現実解は単一統合ではなく連携（federation）＋標準化であり、日本の全国医療情報プラットフォーム構想はこの方向にあります。残る最大の非技術的障壁は、依然として日本の制度的空白（C11）です。
